## 1. 원천 데이터와 보여주는 문서를 분리하라

### 결론
**사람이 읽는 문서(Google Docs, 엑셀, 웹페이지)를 데이터 저장소로 쓰지 마라.** 데이터는 별도 저장소(DB, 파일)에 두고, 문서는 거기서 만들어내는 *결과물*로 취급하라.

### 실무 비유 — EAI 인터페이스
카드사 EAI를 생각해보자. 원장 시스템의 데이터가 진짜고, 상대계에 보내는 **전문(電文)은 그걸 포맷팅한 결과물**이다. 만약 전문 자체를 원장으로 쓴다면 어떻게 될까?

- 같은 거래가 두 번 전송돼도 알 수 없다 (PK 제약이 없으니까)
- 포맷을 바꾸려면 이미 보낸 전문을 전부 찾아 수정해야 한다
- "7월 거래 중 금액 100만원 이상"을 조회할 방법이 없다

autoNote가 정확히 이 상태였다. Google Docs가 유일한 저장소였다.

### 실제로 일어난 일

| 문제 | 실측 | 저장소가 따로 있었다면 |
|---|---|---|
| 같은 글이 최대 5번 중복 기록 | 298블록 | `UNIQUE(채널ID, 메시지ID)` 제약으로 원천 차단 |
| 날짜가 하루씩 밀려 기록됨 | 902건 | 포맷은 화면 그릴 때 결정 → 다시 그리면 끝 |
| 잘못된 내용이 기록됨 | 1,148블록 | 분석 결과가 저장돼 있으니 다시 그리면 끝 |
| 내용 수정이 문자열 수술 | 도구 5개 제작 | `UPDATE` 한 줄 |
| 중복을 눈으로 못 봄 | 몇 주간 미발견 | `GROUP BY ... HAVING COUNT(*)>1` |

복구를 위해 만든 스크립트가 다섯 개였다: `repair_docs`, `restore_docs`, `strip_title_lines`, `relabel_dates_kst`, `dedupe_archive`. **저장소가 따로 있었다면 전부 "다시 렌더링" 한 번으로 끝났다.**

### 새 프로젝트 체크리스트
- [ ] 이 시스템의 **원천 데이터는 어디에 있는가?** 한 문장으로 답할 수 있어야 한다
- [ ] 사람이 보는 화면/문서를 지워도 원천에서 **다시 만들 수 있는가?**
- [ ] 중복을 막는 **유일 키(PK)** 가 정의돼 있는가?
- [ ] 원천은 **추가만 하고 수정하지 않는가** (append-only)?

> 저장소는 거창할 필요 없다. **SQLite 파일 하나면 충분하다.** 대학 때 배운 스키마·테이블·PK 개념 그대로 쓰면 된다. 폐쇄망에서도 문제없다(파일 기반, 설치 불필요).

## 2. 실패를 성공으로 보고하지 마라

### 결론
**부작용이 있는 함수(파일 쓰기, API 호출, DB 갱신)는 "실제로 됐는지 확인한 결과"만 성공으로 반환하게 하라.**

### 실무 비유 — 인터페이스 응답코드
FEP에서 상대계로 전문을 보냈는데 응답코드가 `0000`(정상)으로 왔다. 그런데 실제로는 상대계가 그 전문을 버렸다. 이런 시스템을 운영해본 적 있는가? 장애가 나도 모니터링에 안 잡히고, 정산 때가 되어서야 터진다.

autoNote에 이런 함수가 **세 개** 있었다.

```python
def apply_sepia_theme(self, doc_id):
    try:
        ...문서 배경색 변경 시도...
    except Exception as e:
        print(f"info: {e}")
        return True          # ← 실패해도 성공으로 보고
```

### 실제로 일어난 일

| 함수 | 겉보기 | 실제 |
|---|---|---|
| `apply_sepia_theme` | "테마 적용 완료" 로그 | 지원하지 않는 기능을 호출 → 아무것도 안 됨 |
| `overwrite_text` | True 반환 | 문서 전체 치환은 API 제약상 **애초에 불가능**했음 |
| `batch_update` | True 반환 | 로그만 찍고 아무 동작 없음 |

세 함수 모두 **몇 주간 정상으로 보였다.** 발견된 건 사용자가 "왜 문서 배경이 검은색이지?"라고 물었을 때다.

### 새 프로젝트 체크리스트
- [ ] `except: return True` 형태가 있는가? → **전부 제거**
- [ ] 외부 시스템에 쓴 뒤 **다시 읽어서 확인**하는가?
- [ ] 함수가 True를 반환할 때, 그게 "요청을 보냈다"인지 "실제로 반영됐다"인지 명확한가?

## 3. AI가 실패하면 지어내지 말고 멈춰라

### 결론
**AI 호출이 실패했을 때의 대비책(fallback)은 "내용을 대신 만들어내기"가 아니라 "중단하고 알리기"여야 한다.**

### 실무 비유 — 장애 시 임의 보정
원장 조회가 안 될 때, "대충 어제 잔액으로 채워 넣고 정상 응답"하는 인터페이스를 만들면 어떻게 되겠는가. 고객은 틀린 잔액을 보고, 아무도 장애를 모른다.

### 실제로 일어난 일

autoNote는 API 키가 `dummy-key`(진짜 키가 아닌 더미 문자열)로 설정돼 있었다. **모든 AI 호출이 401 인증 실패**였다. 그런데 코드에 이런 대비책이 있었다.

```python
def _rule_based_weekly_review_fallback(self):
    return """...LTA 비중이 70%에 달해...유가(100달러 선)...
              2027~2028년까지 장기화..."""   # ← 원문에 없는 수치를 지어냄
```

결과: **8개 문서 435블록 중 1,148개의 창작 문구**가 사용자 문서에 기록됐다. 사용자는 그걸 "저자의 실제 분석"으로 읽고 있었다.

| 문서 | 전체 블록 | 창작 오염 |
|---|---|---|
| 반도체사이클 | 283 | 811개 문구 |
| 시장심리·수급 | 88 | 124 |
| 환율·매크로 | 35 | 126 |
| 금리 | 16 | 62 |

정리하는 데 **repair 워커 호출 52회, 650만 토큰, 44분**이 들었다.

### 새 프로젝트 체크리스트
- [ ] AI 호출 실패 시 **아무것도 기록하지 않고 중단**하는가?
- [ ] 실패한 항목의 상태를 저장하지 않아 **다음 실행에서 자동 재시도**되는가?
- [ ] AI가 만든 내용이 **원본에 근거하는지 프로그램이 대조**하는가?

> autoNote는 사후에 "근거 검증"을 넣었다: AI가 뽑아낸 근거에 있는 **숫자가 원문에 실제로 있는지** 문자열 대조한다. 토큰 0원이고, 창작을 잡아내는 데 매우 효과적이었다. 새 프로젝트에는 처음부터 넣을 것.

## 4. 검증은 문서가 아니라 코드에 넣어라

### 결론
**"운영 시 주의사항"을 문서에 적어두는 것으로 끝내지 마라. 지켜지지 않으면 시스템이 거부하게 만들어라.**

### 실무 비유 — 운영 가이드 vs 시스템 강제
"작업 전 반드시 백업할 것"이라고 운영 가이드에 적어둔다고 실수가 사라지던가. 진짜 방법은 **백업 없이는 작업 스크립트가 안 돌아가게** 만드는 것이다.

### 실제로 일어난 일

autoNote 런북에 이렇게 적혀 있었다.
- "08:50 배치와 겹치지 않게 실행할 것"
- "`--limit 1000` 옵션을 붙일 것"

둘 다 지켜진다는 보장이 없었다. 그래서 코드로 옮겼다.

| 런북에 적힌 규칙 | 코드로 옮긴 방법 |
|---|---|
| 배치 시간대 피하기 | 문서 변경 전 **잠금 파일 획득**, 실패 시 종료 |
| `--limit 1000` 붙이기 | **기본값을 1000으로** 변경 |

잠금은 실제로 점유한 상태에서 테스트해 **차단되는 것을 확인**했다.

### 새 프로젝트 체크리스트
- [ ] 런북/가이드에 적은 "주의사항"이 있는가? → 코드로 옮길 수 있는지 검토
- [ ] 위험한 기본값이 있는가? → 안전한 쪽을 기본값으로
- [ ] 동시 실행이 위험한 작업에 **잠금**이 있는가?

## 5. 판단만 AI에게, 나머지는 프로그램에

### 결론
**AI는 비싸고 부정확하다. 규칙으로 처리 가능한 일은 전부 프로그램이 하고, 진짜 판단이 필요한 것만 AI에게 넘겨라.**

### 실무 비유 — 사람이 할 일과 시스템이 할 일
운영에서 알람이 왔을 때, "로그 수집·집계·임계치 비교"는 시스템이 하고 사람은 "그래서 조치할 것인가"만 판단한다. 사람에게 로그를 수동으로 세라고 하지 않는다.

### 실제 분담 (autoNote 최종 형태)

| 프로그램이 담당 (비용 0) | AI가 담당 |
|---|---|
| 데이터 수집, 중복 검사, 진행 상태 저장 | 이 글이 분석 가치가 있는가 |
| 문자열 서식·식별자 생성 | 핵심 주장·근거·논리 추출 |
| 문서 쓰기·읽기 검증 | 주제 분류 (정해진 목록 중 선택) |
| **근거 검증** (숫자 대조) | 주간 종합·관점 변화 |
| 프롬프트 묶어 보내기(배치) | |

### 토큰 실측 — 배치의 중요성

AI 호출 **1건당 약 20,700 토큰이 고정 오버헤드**였다. 짧은 글 하나를 분석하는 데 22,000 토큰이 든다는 뜻이다.

| 방식 | 28건 처리 시 |
|---|---|
| 한 건씩 호출 | 약 264,000 토큰 |
| 묶어서 호출(배치) | 약 140,000 토큰 (**47% 절감**) |

> **주의:** 대량 작업에서는 호출당 토큰이 계속 커졌다(중위 71,000 → 최대 853,000). 원인은 AI 도구가 호출마다 누적된 프로젝트 문맥을 읽어들이기 때문으로 **추정**된다(확정 아님). 비용 동인이 프롬프트 크기가 아니라 **호출 횟수**일 수 있으니, 대량 작업 전에 실측해볼 것.

### 새 프로젝트 체크리스트
- [ ] AI에게 시키는 일 중 **규칙으로 되는 것**이 섞여 있지 않은가?
- [ ] 호출을 **묶어서** 보내는가?
- [ ] 출력 형식을 **스키마로 강제**하는가? (자유 텍스트로 받으면 파싱이 깨진다)
- [ ] 분류 항목은 **선택지 목록(enum)으로 제한**했는가?

> 실측 사례: 주제 분류를 자유 텍스트로 두니 존재하지 않는 주제 `"금지"`가 생성됐다(`"금리"`의 오타). 선택지를 제한하자 모든 모델이 정확해졌다.

## 6. "안 돌았다"를 감지할 수단을 따로 두라

### 결론
**시스템 내부의 알림으로는 "시스템이 아예 안 켜진 경우"를 잡을 수 없다. 밖에서 지켜보는 장치가 필요하다.**

### 실무 비유 — Jennifer와 heartbeat
APM이 애플리케이션 안에서 돌면, 애플리케이션이 죽었을 때 알람도 같이 죽는다. 그래서 별도 감시 서버가 heartbeat를 확인한다.

### 감지해야 할 두 가지

| 유형 | 감지 주체 | autoNote 구현 |
|---|---|---|
| 돌았지만 **실패** | 프로그램 자신 | 예외 포착 → 상태 파일 기록 → 알림 → 종료코드 1 유지 |
| **아예 안 돎** (스케줄러 고장, 서버 꺼짐) | **별도 감시자** | 매일 09:40 별도 스케줄로 마지막 성공 시각 확인 |

전달 경로는 두 개를 병행했다 — 휴대폰 푸시(텔레그램)와 매일 여는 문서에 배너. 하나가 죽어도 다른 하나로 간다. **알림 실패가 본 작업을 중단시키지 않도록** 예외를 격리했다.

### 실제 효과
감시 장치를 붙인 **다음 날 아침 배치가 실패했고, 즉시 잡혔다.** 이전 같으면 종료코드 0으로 조용히 넘어갔을 상황이다.

### 새 프로젝트 체크리스트
- [ ] 실패 시 **사람이 알 수 있는 경로**가 있는가?
- [ ] "아예 안 돈 경우"를 잡는 **별도 감시**가 있는가?
- [ ] 알림이 실패해도 본 작업이 안 죽는가?
- [ ] 같은 이상을 **하루에 한 번만** 알리는가? (알람 피로 방지)

## 7. 경계값은 한 곳에서만 변환하라

### 결론
**시간대·인코딩·단위 같은 것은 시스템 경계에서 딱 한 번 변환하고, 내부에서는 한 가지 기준만 쓴다.**

### 실무 비유 — 인터페이스 전문 표준
대외계마다 날짜 포맷이 다를 때, 각 모듈이 알아서 변환하게 두면 반드시 어딘가 틀린다. 그래서 **수신 어댑터에서 내부 표준으로 한 번 바꾸고**, 내부는 그것만 쓴다.

### 실제로 일어난 일

텔레그램 메시지 시각은 UTC다. 이걸 그대로 `%Y-%m-%d`로 찍었다. 한국 시간은 UTC+9이므로:

```
UTC 08-05 23:51  =  한국시간 08-06 08:51  →  문서에 '2026-08-05' 로 기록
```

**한국 시간 오전 0~9시 글이 전부 전날로 기록됐다.** 사용자가 "왜 어제까지밖에 없지?"라고 물어 발견했다. 총 **902건**.

파급은 날짜 표시만이 아니었다.
- 월별 문서 분류: 9월 1일 오전 글이 8월 문서로 감
- 주간 리포트: 7일 집계 구간이 9시간씩 밀림

### 새 프로젝트 체크리스트
- [ ] 외부에서 들어오는 시각의 **시간대가 무엇인지** 확인했는가?
- [ ] 변환이 **한 곳(공용 함수)** 에서만 일어나는가?
- [ ] 표시용 날짜와 계산용 타임스탬프를 **구분**하는가?

> autoNote 최종 형태: 표시·분류용 날짜는 전부 한국시간, 경과 시간 계산용 타임스탬프는 UTC 유지. 둘을 섞으면 오히려 틀린다.

## 8. AI의 "완료했습니다"를 믿지 마라

### 결론
**AI 에이전트에게 일을 시켰으면, 결과를 그 에이전트에게 묻지 말고 직접 확인하라.**

### 실제 이력 (autoNote에서 AI 에이전트가 한 보고)

| 보고 | 실제 |
|---|---|
| "sepia 기능 추가하고 빌드 완료" | 그 기능이 존재하지 않았음 |
| "테스트 전량 통과" | 2건 실패 중이었음 |
| 문서에 원문 기록 | 인접한 다른 글의 숫자가 섞여 들어감 |
| 문서에 원문 기록 | 원문에 없는 수치(`11억 달러`)가 들어감 |

### 관찰된 패턴

| AI가 잘 하는 일 | AI가 실패한 일 |
|---|---|
| 정해진 프로그램 실행하고 출력 전달 | 즉흥적으로 문서를 직접 편집 |
| 스키마로 강제된 출력 생성 | 스스로 한 일을 검증했다고 보고 |

**대응 방법:**
1. AI에게 문서를 직접 고치게 하지 말고, **결정론적 스크립트를 만들어 실행만** 시킨다
2. 스크립트 안에 **검증을 넣고** 통과 여부를 종료 코드로 낸다
3. 작업 후 **독립적인 확인**을 한 번 돌린다 (5초면 된다)

### 새 프로젝트 체크리스트
- [ ] AI가 하는 일 중 **직접 편집**이 있는가? → 스크립트로 대체
- [ ] AI 보고와 **무관하게** 결과를 확인할 방법이 있는가?
- [ ] 검증이 **자동화**돼 있어 매번 돌리기 쉬운가?

## 착수 전 체크리스트 (복붙용)

새 프로젝트 설계를 AI와 시작할 때 이걸 그대로 붙여넣으면 된다.

```
아래 원칙을 지켜서 설계해줘. 각 항목이 설계에 어떻게 반영됐는지 설명해줘.

[데이터]
1. 원천 데이터 저장소를 화면/문서와 분리할 것 (SQLite 등)
2. 원천은 append-only, 중복 방지 유일 키를 정의할 것
3. 사람이 보는 결과물은 저장소에서 다시 만들 수 있어야 함

[실패 처리]
4. 부작용 있는 함수는 실제 반영을 확인한 뒤에만 성공을 반환할 것
5. AI 호출 실패 시 내용을 지어내지 말고 중단할 것
6. 실패한 항목은 상태를 갱신하지 않아 다음 실행에서 재시도되게 할 것

[검증]
7. AI 출력이 원본에 근거하는지 프로그램이 대조할 것
8. 운영 주의사항은 문서가 아니라 코드로 강제할 것 (기본값·잠금)

[AI 사용]
9. 규칙으로 되는 일은 프로그램이, 판단만 AI가
10. AI 호출은 묶어서(배치), 출력은 스키마로 강제, 분류는 enum으로 제한

[운영]
11. 실패 알림 경로를 둘 것 + "아예 안 돈 경우"를 잡는 별도 감시를 둘 것
12. 시간대/인코딩은 경계에서 한 번만 변환할 것
```

---

## 용어 풀이

| 용어 | 뜻 |
|---|---|
| **fallback (폴백)** | 주 경로가 실패했을 때의 대비 경로 |
| **append-only** | 추가만 하고 수정·삭제하지 않는 방식. 원본 보존에 씀 |
| **스키마 강제 출력** | AI에게 정해진 JSON 구조로만 답하게 하는 것. 파싱 실패를 막음 |
| **enum** | 정해진 선택지 목록. 그 밖의 값은 못 나오게 제한 |
| **배치 호출** | 여러 건을 한 번의 AI 호출로 묶어 보내는 것 |
| **잠금(lock)** | 같은 작업이 동시에 두 번 돌지 못하게 막는 장치 |
| **dry-run** | 실제로 바꾸지 않고 "무엇이 바뀔지"만 출력하는 모드 |
| **heartbeat** | 살아있음을 주기적으로 알리는 신호. 끊기면 이상으로 판단 |

## 이 문서의 한계

- autoNote **한 프로젝트의 경험**이다. 일반 법칙이 아니라 "이런 함정이 있더라"는 사례집으로 볼 것
- "복구 작업의 70~80%가 저장소 설계에서 파생"은 **내 추정**이다. 정밀 측정한 값이 아님
- 토큰 수치는 특정 AI 도구(Antigravity CLI) 실측치다. 다른 도구는 다를 수 있음
- 원 설계에도 이유는 있었다. "AI가 문서에 바로 쓴다"는 방식이 초기에는 빨랐다. **문제는 그 임시 구조가 그대로 운영에 들어간 것**이다
