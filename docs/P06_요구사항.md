# 📋 Phase 6 요구사항 정의서: 하이브리드 오케스트레이터 배치(Daily CLI) 통합

이 문서는 투자 리서치 수집 하이브리드 배치 프로그램의 마지막 단계인 **기동 진입점(CLI) 및 전체 워크플로우 통합 모듈**에 대한 요구사항을 정의합니다.

---

## 1. 개요 및 비즈니스 목적
*   **목적:** 개별적으로 구현된 수집(Collector), 분석(Analyzer), 기록(Writer), 병합(Merger), 리뷰(Reviewer) 서비스를 하나의 CLI 프로그램으로 매끄럽게 연결하여 자동 배치를 완성한다.
*   **해결하려는 문제:** 복잡하게 얽혀 있는 각 파이프라인의 트랜잭션 흐름을 순차적으로 연결하고, 비정상 오류 발생 시 상태 파일(`state.json`)의 원자적(Atomic) 갱신을 통해 데이터 누락과 중복 기록을 철저하게 방지한다.

---

## 2. 기능적 요구사항 (Functional Requirements)

### 2.1 CLI 명령 인터페이스 및 옵션
*   **기동 스크립트 진입점:** `program/src/main.py`
*   **지원 매개변수 (CLI Arguments):**
    *   `--model`: 분석 및 추론에 활용할 LLM 모델명 지정 (기본값: `Gemini 3.5 Flash (Medium)`)
    *   `--channel`: 수집할 텔레그램 채널 ID (기본값: `-1004421517798`)
    *   `--mode`: 실행 모드 스위칭
        *   `batch` (기본값): 전체 일일 배치 프로세스 구동.
        *   `merge`: 생각노트 자동 병합 작업만 즉시 단독 실행.
        *   `review`: 주간리뷰 요약서 생성 작업만 즉시 단독 실행.
        *   `status`: state.json 기준 최종 처리 정보 및 이번 주 처리 통계 보고.

### 2.2 전체 배치 파이프라인 오케스트레이션 워크플로우
`--mode batch` 실행 시 아래 프로세스가 한 번의 트랜잭션 트랙 위에서 순차적으로 기동된다.

1.  **[1단계: 어제 생각 병합]**
    *   `99_생각노트` 구글 문서에서 사용자가 기입해둔 의견(코멘트)을 파싱하여 본문 테마/종목 Docs에 역동기화 치환 병합한다.
2.  **[2단계: 신규 메시지 수집]**
    *   상태 파일(`state.json`)에서 해당 채널의 `last_message_id`를 읽어온다.
    *   텔레그램 MCP 클라이언트를 가동해 신규 등록된 메시지를 100% 빠짐없이 모아 날짜 오름차순으로 정렬한다.
3.  **[3단계: 원문 일괄 보관]**
    *   수집된 모든 메시지를 `00_원문보관 YYYY-MM` 문서의 맨 아래에 그대로 보관 기록한다.
4.  **[4단계: 리서치 분석 및 테마/종목 기록]**
    *   각 수집 메시지에 대해 `is_research` 여부를 판별한다.
    *   참인 분석글인 경우 LLM을 통해 핵심 지식(주장, 근거, 논리, 리스크, 질문)을 추출하고 적절한 테마/종목 구글 Docs에 구조화 서식으로 저장한다.
5.  **[5단계: 오늘 생각노트 Pre-fill 작성]**
    *   금일 추가된 신규 리서치 분석글들에 대한 요약 식별자와 💭 의견 작성란 템플릿을 `99_생각노트` Docs 맨 끝에 추가 개설한다.
6.  **[6단계: 주간 리뷰 점검]**
    *   오늘의 요일이 **토요일**이거나 수동 `--mode review`가 지정된 경우, 최근 7일간 축적된 리서치 정보들을 취합하여 `40_리뷰 YYYY-Wxx`에 성찰 종합 보고서를 기록한다.
7.  **[7단계: 상태 갱신 및 결과 보고]**
    *   상기 파이프라인이 **오류 없이 완전히 종료된 경우에만** `state.json` 파일의 `last_message_id`를 갱신 저장한다.
    *   최종 처리 요약 리포트를 출력한다.

## 3. 비기능적 요구사항 (Non-Functional Requirements)

### 3.1 트랜잭션 원자성 및 예외 전파
*   Docs 기록이나 LLM 호출 도중 치명적 에러가 발생한 경우, 상태 파일(`state.json`) 갱신을 생략하고 에러 스택을 정상 노출하며 배치를 크래시 종료시킨다. (다음 배치 시 실패 시점부터 안전하게 재시도 유도)
*   일부 메시지 분석 실패 등 비치명적인 건은 예외 로그를 남기고 다음 메시지 처리로 넘어가되, 최종 상태값은 성공한 메시지 ID까지로 안전하게 부분 갱신한다.

### 3.2 테스트 가용성 (Testability)
*   전체 파이프라인의 체이닝이Mocking 환경에서 결함 없이 유기적으로 연동되는지 pytest 통합 검증을 완비한다.
*   CLI 파싱, 메인 오케스트레이터의 분기 및 예외 복구 로직의 코드 커버리지 95% 이상을 달성한다.
