# 📋 Phase 1 요구사항 정의서: 텔레그램 수집 및 중복 검사

이 문서는 투자 리서치 수집 하이브리드 배치 프로그램의 첫 번째 단계인 **텔레그램 메시지 수집 및 중복 검사 모듈**에 대한 비즈니스 및 기능적 요구사항을 정의합니다.

---

## 1. 개요 및 비즈니스 목적
*   **목적:** 투자 리서치 채널의 대화 원문 메시지를 유실 없이 안전하게 긁어와 중복 수집 없이 후속 분석 단계(Phase 2)에 전달한다.
*   **해결하려는 문제:** 기존 에이전트 자율 수집 시 메시지 유실, 중복 수집, 비정상 기동 종료 문제를 극대화된 프로그램 통제 하에 해결한다.

---

## 2. 기능적 요구사항 (Functional Requirements)

### 2.1 텔레그램 채널 수집 대상
*   **기본 채널:** `피터케이 채널(26년 하반기)` (채널 ID: `-1004421517798`)
*   **수집 API:** 텔레그램 MCP 서버의 메시지 수집 도구(`list_messages` 또는 `get_history` 등)를 호출하여 텔레그램 서버와 직접 통신한다.

### 2.2 메시지 분류 및 분석 대상 선별 규칙 (중요)
*   **원문 보관소 기록 대상:** 텔레그램 채널의 **모든 메시지** (잡담, 공지, 링크 등 종류 불문 100% 수집 및 보관).
*   **테마/종목 분석 대상 선별 규칙 (분석 제외 대상):**
    *   URL 제외 실제 코멘트/분석 텍스트가 3줄 이하이거나 아예 없는 경우 (단순 링크글 및 짧은 인사말 등)
    *   광고, 제휴, 공구, 쿠팡 파트너스 공유 글
    *   채널 공지사항 및 정기 투표/설문조사 메시지
*   *보고사항:* 분석에서 제외(건너뜀)된 글의 총개수(M건)를 집계하여 최종 배치 보고에 노출해야 한다.

### 2.3 중복 수집 방지 및 추적 (상태 관리)
*   **상태 파일 경로:** `D:\autoNote\data\state.json`
*   **동작 매커니즘:**
    1.  배치 기동 시 `state.json`을 읽어 가장 마지막으로 수집 완료한 `last_message_id`를 확인한다.
    2.  텔레그램 채널에서 `last_message_id`보다 **큰 ID를 가진 모든 메시지**를 수집 범위로 설정한다. (며칠 밀려 있더라도 한 번에 추적 복구)
    3.  `state.json` 파일이 존재하지 않는 경우, 안전장치로 **최근 24시간 동안** 등록된 메시지를 시작점으로 설정하여 수집하고 `state.json` 파일을 새로 자동 생성한다.

### 2.4 안전한 상태 갱신 (Atomicity)
*   수집한 메시지들을 후속 파이프라인(LLM 분석 및 구글 Docs 업로드)으로 전달하여 **구글 Docs 기록까지 완전히 성공한 경우에만** `state.json`의 `last_message_id`를 갱신한다.
*   중간 단계에서 에러가 발생한 경우 해당 메시지 ID는 갱신되지 않으며, 다음 배치 기동 시 실패한 메시지부터 다시 수집을 재시도해야 한다.

---

## 3. 비기능적 요구사항 (Non-Functional Requirements)

### 3.1 성능 및 안정성
*   **재시도 로직:** 텔레그램 API/MCP 응답 지연 혹은 일시적 네트워크 장애 발생 시 최대 3회 재시도(Exponential Backoff)를 수행한다.
*   **메모리 풋프린트:** 한 번에 수집하는 메시지가 100건을 초과하더라도 메모리 누수가 없도록 제너레이터(Generator) 패턴이나 청크 단위 처리를 도입한다.

### 3.2 테스트 가용성 (Testability)
*   실제 텔레그램 API 통신 없이도 비즈니스 로직을 검증할 수 있도록 텔레그램 클라이언트는 **인터페이스(추상화)로 분리**하며, 유닛 테스트 시 **Mock 객체**를 지원해야 한다.
*   `pytest`를 사용하여 수집 및 필터링 로직에 대한 코드 커버리지 95% 이상을 달성한다.
