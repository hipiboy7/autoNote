## 2. 문제 1 — ESS 테마는 만들 수 있는 구조가 아니었다

테마는 8개 고정 enum 이었고(`analyzer/service.py`), 문서도 테마 1개 = 문서 1개로
하드코딩돼 있었다(`main.py`). 시작 시 `verify_theme_mappings()` 가 검사하는 것은
**"THEMES 에 빠진 문서가 있는가"** 뿐이고, 반대 방향 — *새 테마가 나타나면 문서를
만든다* — 는 경로가 아예 없다.

의도된 설계다. `service.py` 주석에 *"자유 문자열로 두면 존재하지 않는 테마가 생성되고
라우팅이 조용히 폴백해 오분류가 쌓인다"* 고 적혀 있다. 원문보관 문서는
`OriginalDocRegistry` 가 자동 생성하지만 테마 문서에는 그 장치가 없다.

따라서 ESS 글이 들어와도 8개 중 하나로 강제 매칭될 뿐이었다. **새 문서는 원리상
생길 수 없었다.**

## 3. 문제 2 — 배치가 나흘째 죽어 있었다 (이게 진짜였다)

`state.json` 이 말해주고 있었다.

```
last_message_id  : 979
last_run         : 2026-08-14 09:16 KST   ← 마지막으로 상태가 전진한 시점
last_batch_result: "fail"
last_batch_at    : 2026-08-18 09:43 KST
last_alert_date  : "2026-08-18"           ← 경보는 나가고 있었다
```

에러는 `message [983, 985, 986, 987] 분석이 재시도 후에도 통과하지 못했습니다` 였고,
`analyze_batch` 는 **전원 통과를 요구**하므로(`service.py:100`) 4건이 막히면 그날
배치 전체가 쓰기 단계 전에 중단된다. 그래서 ESS 문서만이 아니라 **아무것도 안 쓰였다.**

### 트러블슈팅 과정

**(1) 원문부터 봤다.** 텔레그램에서 읽기 전용으로 983~1028 을 가져왔다.
983 은 148자 인사말, 985 는 ESS 예고, 986·987 은 OBBBA/ESS 본문이었다.
`extract` 의 `batch_size` 가 4 이므로 이 4건이 **정확히 한 청크**였다.
이 시점의 가설은 "근거 없는 인사말 때문에 모델이 출력을 길게 쓰다 잘렸다" 였다.

**(2) 격리 재현으로 가설이 깨졌다.** 재시도를 끄고 부분집합으로 나눠 돌렸더니
**네 실험이 전부 실패했다.**

| 실험 | 결과 |
|---|---|
| 983+985+986+987 | 실패 |
| 986+987 (내용 있는 ESS 글) | 실패 |
| 983 단건 | 실패 |
| 985 단건 | 실패 |

단건도 실패한다는 것은 메시지 내용·청크 크기·ESS 와 **무관**하다는 뜻이었다.
가설을 버리고 agy 쪽을 봤다.

**(3) 원 응답 봉투를 직접 열었다.** 결정적이었다.

```
status            = ERROR
error             = invalid arguments:
                    - at '/reports/0/risks': got string, want array
structured_output = { ...완벽하게 유효한 dict... }
```

`agy models` 로 확인하니 버전이 **1.1.14**, 봉투에 없던 `error` 키가 생겨 있었다.

> **agy 는 모델이 첫 시도에서 스키마를 어기면 내부 재시도로 바로잡는데,
> 그렇게 성공한 뒤에도 `status=ERROR` 를 남기고 첫 위반을 `error` 에 기록한다.**
> 즉 `status=ERROR` 와 `structured_output` 유효는 **동시에 성립한다.**

우리 코드(`agy_cli.py`)는 status 만 보고 멀쩡한 결과를 버리고 있었다.
필수 필드가 6개인 extract 는 첫 시도 위반이 사실상 매번 나므로 100% 실패했고,
스키마가 단순한 triage 는 SUCCESS 라 살아남았다. 8/14 까지 멀쩡하던 배치가
8/15부터 죽은 것도 이 업데이트 시점과 맞는다.

### 수정

스키마를 요구한 호출은 **`structured_output` 유효성**을 판정 기준으로 삼는다.
스키마가 없으면 판정 근거가 없으므로 status 를 그대로 신뢰한다(review 워커가 이 경로).
안전망은 그대로다 — analyzer 가 pydantic 검증 + 원문 근거 대조를 하므로 엉터리
출력은 다음 단계에서 걸린다.

회귀 테스트 3건을 추가했고, 전제가 바뀐 기존 테스트 1건은 새 계약에 맞게 고쳤다.
(`status=ERROR` 여도 회수 가능하면 성공 / 회수 불가면 실패 / 스키마 없으면 기존대로 실패)

**운영 검증:** 이번 배치의 워커 호출 **11번이 전부 `status=ERROR`** 였고 전부 구조화
출력을 회수했다. 고치지 않았다면 triage 첫 호출부터 실패해 배치가 시작도 못 했다.

## 7. 오늘 얻은 교훈

- **외부 도구의 응답 계약은 말없이 바뀐다.** agy 1.1.14 는 `error` 키를 추가하고
  status 의 의미를 바꿨는데 우리는 나흘 뒤에야 알았다. 도구 버전과 봉투 구조를
  주기적으로 확인할 근거가 필요하다.
- **`status` 하나로 성공/실패를 판정하면 안 된다.** 판정은 *원하는 산출물을 얻었는가*
  로 해야 한다. structured_output 이 유효한데 status 때문에 버린 것이 이번 사고다.
- **가설이 그럴듯할수록 격리 실험으로 깨봐야 한다.** "인사말이라 출력이 길어져 잘렸다"
  는 잘린 위치까지 맞아떨어져 설득력이 있었지만 완전히 틀렸다. 단건 재현 한 번이
  가설을 뒤집었다.
- **전원 통과 방식은 1건이 막히면 그날 전체를 세운다.** 근거 없는 기록을 막으려는
  의도는 옳지만 입도가 너무 크다. 실패 건만 격리하고 나머지는 기록하는 편이 안전하다.
