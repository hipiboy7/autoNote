## 2. 오늘의 실증 — VM 이 꺼져 있어도 배치가 돌았다

사용자 보고: **"오늘 VM 이 08:50 넘어까지 off 되어 있었다."** 사실이었고, 그럼에도 배치는 완주했다.

| 시각 (KST) | 일 |
|---|---|
| 08:50:00 | 예정 시각 — **VM off, 트리거 놓침** |
| 08:50:21 | VM 부팅 |
| **08:55:55** | **`autoNote_DailyBatch` 자동 기동** (부팅 5분 34초 후), 종료 코드 0 |
| 09:00:49 ~ 09:09 | 워커 7회 호출 |
| 09:12:47 | 배치 완료 — `last_batch_result: "ok"` |
| 09:40:40 | `autoNote_HealthCheck` 실행, 종료 코드 0 (정상 판정 → 알림 없음) |

### 왜 돌았나 — 어제 고친 그 설정이다

`autoNote_DailyBatch` 의 **`StartWhenAvailable = True`** ("예약된 시작을 놓치면 가능한 한 빨리 실행").

커밋 `7bd8838` 에 *"기본값 False 라 VM 이 08:50 에 꺼져 있으면 그날 배치가 영영 돌지 않는다"* 고 적어두신 시나리오가 **하루 만에 실제로 발생했고, 고친 대로 동작했다.** 8/10 문서의 최우선 확인 항목("스케줄러 환경에서도 통하는가")도 이것으로 해소됐다.

### 현재 스케줄 작업 설정 (실측)

## 3. 논의한 방안 — 사용자 제안과 그 평가

### 사용자 제안 (원문 취지)

> VM 이 켜지면 08:50 이 지났는지 확인 → 지났으면 배치가 돌았는지 확인 → 안 돌았으면 실행,
> 잘 돌았으면 정상 수행 여부 알람.

논리는 맞다. 다만 앞 세 단계는 이미 있는 것과 겹치고, **실제로 비어 있는 칸은 두 개**다.

| 제안 단계 | 현재 |
|---|---|
| 08:50 지났는지 체크 | `StartWhenAvailable` 이 대신함 |
| 배치가 돌았는지 확인 | 09:40 워치독이 `state.json` 으로 판정 중 |
| **안 돌았으면 실행** | **없음** — 워치독은 알리기만 하고 고치지는 못한다 |
| **잘 돌았으면 정상 알람** | **없음** — 지금은 이상할 때만 알린다 |

### 설계 시 반드시 반영할 네 가지

1. **"VM 이 켜지면" 은 지금 구조에서 "로그인하면" 이다.**
   두 작업 모두 `LogonType: Interactive` — SYSADMIN 이 대화형 로그인을 해야 돈다. 부팅만 하고
   로그인을 안 하면 배치도 워치독도 침묵한다. **오늘 5분 만에 돈 것은 부팅 직후 로그인하셨기 때문**이다.
   ONSTART 트리거로 걸어도 이 전제는 안 풀린다. 자동 로그온을 켜거나 로그온 트리거로 명시하거나 둘 중 하나.
   → "사용자 로그온 여부와 관계없이 실행"은 agy·MCP 가 대화형 세션에 의존할 가능성이 커서 **권하지 않음**.

2. **판정 기준은 시계가 아니라 `state.json` 으로.**
   "지금 08:50 지났나" 대신 **"`last_batch_at` 의 날짜가 오늘인가"**. 부팅 시각·재부팅 횟수와 무관하게 항상 맞다.
   `packages/app/src/autonote/batch_health.py` 에 판정 로직이 이미 있으니 재사용한다.

3. **중복 실행 방지.** 부팅 스크립트와 `StartWhenAvailable` 이 둘 다 발동하면 배치가 두 번 돈다.
   `IgnoreNew` 는 *동시* 실행만 막고 5분 간격 순차 실행은 못 막는다. 2번의 날짜 가드가 이것도 해결한다.

4. **정상 알람은 매번 띄우면 무시하게 된다.** 하루 1회로 제한하고, 성공은 Windows 토스트(로컬·조용),
   실패는 텔레그램으로 채널을 나누는 것을 권장.

### 선택지 — **내일 여기서부터 시작한다**

> ⚠️ 어제 문서의 "정리안 A/B/C"(사용량 로그 78행 처리)와 **다른 목록**이다. 혼동 주의.
> 이 표는 **스케줄 복구안 A~D**.

| 안 | 내용 | 비용 | 메모 |
|---|---|---|---|
| **A** | **워치독 자가치유** — 09:40 점검에서 "오늘 안 돌았음"을 발견하면 알림만 하지 말고 배치를 직접 기동 | 작음 | 새 작업 등록 불필요. `run_watchdog()` 에 분기 하나 |
| **B** | **로그온 트리거 + 날짜 가드** — 로그온 시 오늘자 기록이 없으면 배치 실행 | 중간 | 사용자 제안에 가장 가까움. 늦게 로그인해도 그날 안에 회수 |
| **C** | **정상 여부 알람** | 작음 | 하루 1회 제한 필수. 채널(토스트/텔레그램) 결정 필요 |
| **D** | `DisallowStartIfOnBatteries` → False | 1줄 | 현재 True. VM 은 보통 AC 로 보고하지만 조용히 건너뛸 조건 |

**제안한 순서: A + D 먼저 → C(채널 정한 뒤) → B(자동 로그온 여부 정한 뒤).**

A 를 먼저 두는 이유: 워치독이 이미 매일 09:40 에 판정까지 하는데 **고칠 능력만 없다.** 분기 하나로
"감시자"가 "복구자"가 된다. B 는 회수가 더 빠르지만(로그온 즉시) 1번 전제를 정리하지 않으면 A 와 같은 한계를 공유한다.

> **미결:** 사용자가 A~D 중 어느 조합으로 갈지 아직 고르지 않았다. **내일 이것부터 확정할 것.**

## 5. 오늘 얻은 교훈

- **고친 것이 실제로 통하는지는 실전에서만 알 수 있다.** `StartWhenAvailable` 은 어제 넣었고 오늘
  정확히 그 조건(VM off at 08:50)이 발생해 검증됐다. 이런 검증 기회는 놓치지 말고 기록해 둔다.
- **감시와 복구는 다른 능력이다.** 워치독은 "안 돌았다"를 정확히 알지만 아무것도 못 한다.
  판정 로직을 이미 갖춘 곳에 실행 권한을 주는 것이 새 감시자를 만드는 것보다 싸다.
- **"VM 이 켜지면" 과 "로그인하면" 은 다르다.** 대화형 로그온에 묶인 작업은 부팅만으로는 안 돈다.
  무인 운영을 원하면 이 전제부터 정리해야 한다.
- **상태 판정은 시계보다 기록으로.** "지금 몇 시인가"는 부팅 시각·재부팅·시간대에 흔들리지만
  "오늘자 성공 기록이 있는가"는 흔들리지 않는다.
