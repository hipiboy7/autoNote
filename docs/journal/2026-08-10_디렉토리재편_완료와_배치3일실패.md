## 1. 배치 3일 실패 — 원인과 복구

### 무슨 일이 있었나

| 날짜 (KST) | 결과 |
|---|---|
| 08/07 08:50 | 성공 — message ID 836 까지 |
| 08/08 · 08/09 · 08/10 08:50 | **실패** — `RuntimeError: Telegram MCP 서버가 응답 없이 스트림을 닫았습니다.` |
| 08/10 (수동 실행) | 성공 — ID 862 까지, 밀린 26건 전부 회수 |

### 원인

8/7 세션에서 `telegram-mcp/` 를 `vendor/telegram-mcp/` 로 옮기면서, **코드 안의 기본 경로를 안 고쳤다.**

```python
# packages/libs/telegram-client/src/telegram_client/mcp_client.py
DEFAULT_MCP_DIR = r"D:\autoNote\telegram-mcp"   # 이동 후 존재하지 않는 경로
```

`.env` 에 `TELEGRAM_MCP_DIR` 항목이 없어 이 기본값이 그대로 쓰였다. 없는 경로로 MCP 서버를
띄우니 프로세스가 즉시 죽었고, JSON-RPC 핸드셰이크가 빈 스트림을 읽었다.

### 왜 3일이나 걸렸나 — 이게 진짜 문제다

원인이 세 겹으로 가려져 있었다.

1. **에러 메시지가 원인을 감췄다.** "응답 없이 스트림을 닫았습니다" 는 증상이지 원인이 아니다.
   경로가 틀렸다는 사실이 어디에도 안 나왔다.
2. **테스트가 이 구멍을 통과시켰다.** 기존 테스트는 `MCPTelegramClient(mcp_dir="x")` 처럼
   존재하지 않는 문자열을 넘기고 `Popen` 을 mock 했다. 실제 경로가 맞는지 아무도 안 물었다.
   디렉토리를 옮겨도 테스트는 초록불이었다.
3. **옮긴 뒤 한 번도 안 돌려봤다.** 같은 세션에서 "옮기고 안 돌려보면 조용히 깨진다" 고
   써 놓고 `--mode status` 를 안 돌렸다. 한 번만 돌렸으면 즉시 잡혔다.

## 1-2. 파생 발견 — 워치독의 스케줄러 이력이 늘 "정상" 이었다

배치 실패 3일 동안 스케줄러 이력을 보니:

| 작업 | 마지막 결과 |
|---|---|
| `autoNote_DailyBatch` | **1** (실패 — 사실과 일치) |
| `autoNote_HealthCheck` | **0** (정상 — 사실과 불일치) |

판정 로직(`batch_health.evaluate_batch_health`)은 `last_batch_result == "fail"` 을 정확히
이상으로 잡는다. 문제는 그 위층이었다.

```bat
python cli\check_batch_health.py
if %ERRORLEVEL% EQU 1 echo [ALERT] ...   ← echo 가 ERRORLEVEL 을 0 으로 덮어쓴다
endlocal                                  ← 종료 코드 0 으로 끝난다
```

**`echo` 가 `ERRORLEVEL` 을 0 으로 만들고, bat 이 그대로 끝났다.** 워치독이 무엇을 판정하든
스케줄러 이력에는 언제나 0 이 남는다. 감시자를 감시할 수단이 없었다는 뜻이다.

`endlocal & exit /b %RC%` 로 고쳤고, 가짜 실패 상태를 만들어 **종료 코드 1 이 실제로
전파되는 것까지 확인**했다.

### 알림이 사용자에게 닿았는지 — 확인된 것과 추정

- **확인됨:** `run_daily_batch.bat` 은 `exit /b` 가 있어 실패가 이력에 남았다 (결과 1)
- **확인됨:** 알림의 텔레그램 경로는 실패의 원인인 바로 그 `MCPTelegramClient` 를 쓴다
  (`main.py:430`, `check_batch_health.py:38`)
- **추정:** 따라서 3일 동안 텔레그램 알림은 실패했을 가능성이 높다. Docs 경로는 독립적이라
  생각노트에 기록됐을 수 있으나, 확인하지 않았다
- **확인 불가:** `last_alert_date` 는 오늘 배치 성공 시 `None` 으로 초기화되므로
  (`collector/service.py:132`) 과거 발송 여부를 사후에 알 수 없다

> **설계 결함.** 알림 경로가 감시 대상과 같은 부품에 의존하면, 정작 필요한 순간에 침묵한다.
> 텔레그램 MCP 가 죽으면 "텔레그램 MCP 가 죽었다" 는 알림도 못 간다.
> 이건 코드 수정이 아니라 설계 판단이 필요해 **사용자와 상의 후 결정할 사항으로 남긴다.**

### 고친 것

| 대상 | 조치 |
|---|---|
| `telegram_client/mcp_client.py` | 절대 경로 → `Path(__file__).parents[5] / "vendor" / "telegram-mcp"` (저장소 루트 역산) |
| 같은 파일 `_call_tool` | `Popen` 전에 `main.py` 존재 확인, 없으면 **경로를 찍어서** 중단 |
| `google_docs_client/google_auth.py` | `DEFAULT_DECRYPT_SCRIPT` 도 동일하게 루트 역산으로 전환 |
| `telegram-client` 테스트 | `mcp_dir="x"` → `main.py` 가 실재하는 tmp_path 픽스처 |
| 신규 테스트 2건 | 기본 경로가 **실제로 존재하는지** 검증 (`vendor/telegram-mcp`, `ops/tools/decrypt_token.js`) |

마지막 항목이 재발 방지의 핵심이다. 이제 이 디렉토리를 옮기면 배치가 아니라 **테스트가 먼저 깨진다.**

## 4. 이번 건에서 배운 것

**"옮겼다" 와 "동작한다" 는 다른 명제다.** 이동은 git 이 보증하지만 참조는 아무도 보증하지 않는다.
파일 이동 뒤에는 반드시 진입점을 한 번 실행한다. 미들웨어로 치면 인스턴스 경로를 바꾸고
기동 스크립트만 고친 채 실제 기동을 안 해본 것과 같다.

**테스트가 초록불이라고 안전한 게 아니다.** mock 이 실제 환경을 가리면, 테스트는 코드가 아니라
mock 을 검증한다. 외부 자원(경로·파일·프로세스)에 의존하는 부분은 **최소 한 건은 실재를 확인**해야 한다.
