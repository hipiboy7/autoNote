## 4. 오늘 고친 것

### ① agy 실패 원인이 안 보이던 문제 (커밋 `1394da0`)

러너가 0 아닌 종료 코드를 만나면 **stderr 만 기록하고 stdout 을 버리고 있었다.**
그런데 agy 는 실패 원인을 stdout 봉투에 적는다. 리뷰가 3주간 실패하는 동안 원인이
내내 stdout 에 있었는데 로그에는 `exit=1 stderr=` 만 남았다.

```
이전:  exit=1 stderr=
이후:  exit=1 status=ERROR error=timeout waiting for response stderr=(없음)
```

`_failure_detail()` 이 봉투를 파싱해 status/error 를 앞세우고, 파싱이 안 되면
stdout 원문을 싣는다. stderr 가 비면 `(없음)` 을 명시한다 — 예전 `stderr=` 는
"비었다"와 "기록 안 했다"가 구분되지 않아 진단을 헷갈리게 했다. 회귀 테스트 2건 추가.

### ② 워치독 사각지대 (미커밋)

**먼저 세운 대책이 틀렸다.** "허용치를 24시간으로 낮추면 된다"고 판단했는데, 실제
숫자를 넣어보니 8/25 배치가 10:16 에 늦게 끝나 8/26 09:40 시점 경과가 **23.4시간**
이었다. 24시간으로 낮춰도 통과한다. **직전 배치가 늦을수록 다음 날 미실행을 못 잡는**
구조적 한계다.

그래서 나이 규칙은 안전망으로 두고 날짜 규칙을 추가했다.

> 현지 기준 마감 시각(`BATCH_DUE_DEADLINE_HOUR`, 기본 11시)을 넘겼는데
> **오늘자 배치 기록이 없으면** 이상.

마감을 11시로 잡은 이유는 회수 실행 때문이다. 8/25 배치가 10:16 에 끝났으므로 더
이르면 정상 회수를 오탐으로 잡는다. `BATCH_MAX_AGE_HOURS` 를 기본값보다 크게 잡으면
(격일 배치 선언) 날짜 규칙은 적용하지 않는다 — 기존 계약을 깨지 않기 위해서다.

**스케줄도 함께 옮겼다**: `autoNote_HealthCheck` 09:40 → **11:10**. 마감보다 이르면
새 규칙이 발동하지 않아 코드만으로는 효과가 없다. 트리거만 교체했고 액션·설정은
보존했다. `AGENTS.md`·`README.md`·`check_batch_health.py` 의 09:40 표기도 갱신했다.

검증: 오늘 아침 상황 재현 시 09:40 점검은 여전히 '정상', 11:10 점검은 '이상' 판정.
실제 워치독 실행도 정상(종료코드 0, 알림 없음).

## 6. 오늘 얻은 교훈

- **대책을 세우기 전에 실제 숫자를 넣어봐야 한다.** "허용치 24시간으로 낮추면 된다"는
  그럴듯했지만 실제 사례(23.4시간)에 대입하니 틀렸다. 대입 한 번이 헛수고를 막았다.
- **한 번 성공했다고 고쳐진 것이 아니다.** 리뷰는 오늘 성공했지만 같은 날 실패도
  재현됐다. 간헐적 실패를 '해결됨'으로 처리하면 다음 주에 같은 자리로 돌아온다.
- **진단 능력에 먼저 투자하면 나머지가 빨라진다.** stdout 을 버리던 3줄 때문에 3주를
  헤맸다. 로그가 원인을 담고 있는지부터 확인할 것.
