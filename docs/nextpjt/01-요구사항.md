# 01. 요구사항 정의서 (초안 — 미결 항목 포함)

> **대상 독자:** 착수 시 요구사항을 확정하는 나 자신 + Claude Code
> **용도:** 무엇을 만들지 합의. **미결(❓) 항목은 첫 세션에서 채운다**
> **상태:** 초안. `gemini.md` 그라운드 룰 5(문서 선행)에 따라 이 문서 확정 후 설계로 넘어간다

---

## 1. 배경과 문제

### 현재 상황
- 투자 리서치 정보가 여러 텔레그램 채널에 흩어져 있다
- 채널마다 볼륨과 품질이 다르고, 관심 없는 글이 대부분이다
- 사람이 전부 읽고 골라내는 것은 지속 불가능하다

### 해결하려는 것
관심 있는 **산업·기업·테마**에 관한 글만 자동으로 골라내 정리한다.

### 해결하지 않는 것 (범위 밖)
명시적으로 적어둔다. 나중에 범위가 번지는 것을 막는다.

- 매매 판단·추천 생성 — **금지**. 이것은 정보 정리 시스템이다
- 가격·차트 데이터 수집 — 텔레그램 텍스트만 다룬다
- 실시간 알림 (몇 초 내) — 배치 처리로 충분하다
- 텔레그램 외 소스 (뉴스 사이트, 트위터 등) — 1차 범위 밖. 확장 여지는 남긴다

---

## 2. 기능 요구사항

### FR-1. 다중 채널 수집

| 항목 | 내용 |
|---|---|
| 대상 | ❓ 채널 목록 미정 — 착수 시 확정 |
| 주기 | ❓ 미정 (autoNote 는 하루 1회 08:50) |
| 범위 | 각 채널의 마지막 처리 지점 이후 전부 |
| 원칙 | **누락 없이, 중복 없이.** 원문은 수정하지 않는다 |

**중요:** 채널별로 진행 지점을 따로 관리한다. autoNote 는 채널 하나라 단일 값이었지만, N개 채널에서는 한 채널이 실패해도 나머지가 진행되어야 한다.

### FR-2. 워치리스트 관리

내가 관심사를 **선언**하고, 시스템이 그에 따라 골라낸다.

| 유형 | 예시 | 매칭 방법 |
|---|---|---|
| 기업 | 삼성전자, SK하이닉스 | 종목명 + 별칭(하이닉스, SKHY) + 티커 |
| 산업 | 반도체, 방산, 2차전지 | 산업 키워드 + 하위 용어(HBM, DRAM…) |
| 테마 | 금리, 환율, AI CAPEX | 테마 키워드 |

- 워치리스트는 **설정 파일로 관리**한다 (코드에 박지 않는다)
- 별칭·오타 변형을 함께 등록할 수 있어야 한다 (`전자닉스` 같은 은어 포함)
- ❓ 초기 워치리스트 항목 미정

### FR-3. 3단 필터

볼륨 대비 비용을 억제하는 핵심 구조. 자세한 근거는 `02-아키텍처.md`.

| 단계 | 방법 | 비용 | 판정 |
|---|---|---|---|
| 1단 | 프로그램 — 워치리스트 사전 매칭 | 0 | 명백히 무관 → 제외, 명백히 관련 → 통과 |
| 2단 | AI 배치 — 관련성 판별 | 낮음 | 애매한 것만 |
| 3단 | AI 배치 — 내용 추출 | 높음 | 관련 확정분만 |

**요구사항:** 1단에서 대부분(❓ 목표 80% 이상?)이 걸러져야 한다. 그렇지 않으면 비용 목표를 못 맞춘다.

### FR-4. 내용 추출

관련 확정된 글에서 다음을 뽑는다.

| 항목 | 설명 |
|---|---|
| 언급된 대상 | 워치리스트 중 어떤 기업·산업·테마인가 (복수 가능) |
| 핵심 내용 | 이 글이 말하는 것 한 줄 |
| 근거 | 글이 제시한 구체 수치·사실 (**원문에 있는 것만**) |
| 성격 | 사실 전달 / 저자 의견 / 전망 중 무엇인가 |

**필수 제약:**
- 원문에 없는 사실·수치를 추가하지 않는다
- 근거의 숫자는 **프로그램이 원문과 대조 검증**한다
- 검증 실패 시 기록하지 않고 재시도 대상으로 남긴다
- 대상 분류는 워치리스트 항목 중에서만 선택한다 (enum 강제)

### FR-5. 결과물 렌더링

| 항목 | 내용 |
|---|---|
| 형태 | ❓ 미정 — Google Docs / 로컬 마크다운 / 텔레그램 다이제스트 |
| 단위 | ❓ 미정 — 관심사별? 날짜별? 둘 다? |
| 원칙 | **저장소에서 만들어내는 결과물.** 지워도 다시 만들 수 있어야 한다 |

### FR-6. 조회

저장소에 직접 질의할 수 있어야 한다. autoNote 에서 "중복이 몇 개인지" 조차 눈으로 세야 했던 문제를 반복하지 않는다.

최소한 이런 질문에 답할 수 있어야 한다.
- 특정 기업이 언급된 글을 날짜순으로
- 어제 수집된 글 중 관련 판정된 것
- 채널별 수집·관련 판정 건수
- 중복 여부, 누락 구간

### FR-7. 운영

| 항목 | 요구 |
|---|---|
| 실패 알림 | 배치가 실패하면 사람이 안다 |
| 미실행 감시 | 배치가 **아예 안 돌아도** 안다 (별도 감시자) |
| 재시도 | 실패한 항목은 상태를 갱신하지 않아 다음 실행에서 자동 재시도 |
| 상태 조회 | 한 명령으로 정상/이상 판정 |
| 토큰 기록 | AI 호출별 사용량 누적 기록 (비용 추적) |

## 3. 비기능 요구사항

### NFR-1. 비용

| 항목 | 목표 |
|---|---|
| 하루 AI 비용 | ❓ 예산 미정 |
| 볼륨 증가 대응 | 글 수가 10배가 되어도 AI 비용은 **2배 이내** |
| 측정 | 토큰 사용량을 기록해 실측으로 검증 |

### NFR-2. 정확성

| 항목 | 목표 |
|---|---|
| 재현율 (놓치지 않기) | ❓ 목표 미정 — 표본 라벨링 후 설정 |
| 정밀도 (헛것 안 섞기) | ❓ 목표 미정 |
| 창작 (없는 내용 생성) | **0건** — 근거 검증으로 강제 |
| 중복 | **0건** — DB 유일 키로 강제 |

### NFR-3. 운영성

- 실패 원인이 로그와 상태 파일에 남는다
- 일회성 보정 작업이 필요하면 스크립트로 만든다 (손으로 데이터를 고치지 않는다)
- 새 환경에서 설치 절차가 문서화돼 있다

### NFR-4. 환경 제약

| 항목 | 내용 |
|---|---|
| 실행 환경 | ❓ 현재 VM 계속? |
| 폐쇄망 고려 | ❓ 필요한가? 필요하면 로컬 모델·오프라인 저장소 전제 |
| 저장소 | SQLite (파일 기반, 설치 불필요 → 폐쇄망에서도 동작) |
| AI | ❓ agy 계속? 다른 백엔드? — **추상화 계층으로 교체 가능하게 설계** |

## 4. 데이터 요구사항

### 원천 (수정하지 않음)

| 항목 | 내용 |
|---|---|
| 무엇 | 채널별 메시지 원문 + 시각 + 작성자 |
| 유일 키 | `(채널ID, 메시지ID)` |
| 원칙 | append-only. 한번 저장하면 수정·삭제하지 않는다 |
| 시각 | ❓ 저장은 UTC, 표시는 KST (autoNote 교훈) — 확정 |

### 파생 (다시 만들 수 있음)

| 항목 | 내용 |
|---|---|
| 관련성 판정 | 어느 단계에서 어떻게 판정됐는지 근거와 함께 |
| 추출 결과 | 대상·핵심·근거·성격 |
| 렌더링 결과물 | 문서/다이제스트 |

**파생 데이터는 재계산 가능해야 한다.** 워치리스트가 바뀌면 다시 판정하고, 프롬프트가 개선되면 다시 추출한다.

## 5. 미결 항목 정리 (첫 세션 체크리스트)

착수 첫 세션에서 이것부터 답하고 이 문서를 갱신한다.

- [ ] 대상 채널 목록 (각 채널의 성격·볼륨 추정)
- [ ] 초기 워치리스트 (기업·산업·테마 각 몇 개)
- [ ] 결과물 형태와 단위
- [ ] 하루 AI 비용 예산
- [ ] 실행 환경 / 폐쇄망 필요 여부
- [ ] AI 백엔드 (agy 유지 여부)
- [ ] autoNote 와 저장소 공유 여부
- [ ] 재현율·정밀도 목표치
- [ ] 표본 라벨링 100건 계획 (측정 기준선)

> **미결 항목을 남긴 채 코딩으로 넘어가지 말 것.** autoNote 는 "일단 돌게 만들고 나중에 정리"로 시작해 임시 구조가 운영에 들어갔다.
