# 00. 프로젝트 개요 — 다중 채널 리서치 수집·추출 시스템

> **대상 독자:** 이 프로젝트를 새 디렉토리에서 Claude Code 와 함께 시작할 나 자신
> **용도:** 착수 시 가장 먼저 읽는 문서. 무엇을 만드는지와 왜 이렇게 만드는지를 담는다
> **읽는 순서:** 00(이 문서) → 01 요구사항 → 02 아키텍처 → 03 디렉토리 → 04 AGENTS.md → 05 착수 절차

## 한 줄 정의

**여러 텔레그램 채널의 글을 전부 모아두고, 그중 내가 관심 있는 산업·기업·테마만 골라내 정리해주는 시스템.**

---

## autoNote 와 무엇이 다른가

기존 `autoNote` 는 **채널 하나, 저자 하나**를 대상으로 "저자의 판단 논리"를 축적하는 시스템이다. 이 프로젝트는 모양이 다르다.

| | autoNote (기존) | 이 프로젝트 (신규) |
|---|---|---|
| 소스 | 1개 채널, 단일 저자 | **N개 채널**, 다수 저자 |
| 하루 볼륨 | 20~30건 | **수백~수천 건** (추정) |
| 목적 | 저자의 판단 논리 축적 | **관심 대상 추출·모니터링** |
| 관심사 | 고정 테마 8개 | **내가 선언하는 워치리스트** (기업/산업/테마) |
| 결과물 | 테마별 지식 문서 | 관심사별 다이제스트 + 조회 가능한 저장소 |
| 핵심 난제 | 논리 추출 품질 | **볼륨 대비 비용 억제** |

**볼륨이 10배가 되어도 AI 비용은 2배 이내로 억제하는 것**이 이 프로젝트의 핵심 설계 목표다.

---

## 왜 새로 만드는가 (기존 것을 확장하지 않는 이유)

`autoNote` 는 **Google Docs 를 유일한 저장소로** 쓴다. 이 선택 때문에 2026-08 에 이틀간 대규모 복구 작업이 필요했다.

| autoNote 에서 겪은 일 | 실측 |
|---|---|
| 같은 글이 최대 5번 중복 기록 | 298블록 |
| 날짜가 하루씩 밀려 기록 | 902건 |
| AI 실패 시 지어낸 내용이 기록 | 1,148건 |
| 복구를 위해 만든 일회성 스크립트 | 5개 |

원인과 교훈은 [`../00-신규프로젝트-설계교훈.md`](../00-신규프로젝트-설계교훈.md) 에 정리돼 있다. **이 프로젝트는 그 교훈을 처음부터 반영한다.** 기존 코드를 확장하면 그 구조를 물려받게 되므로 새로 시작한다.

단, **수집·저장·AI 호출 계층은 개념을 그대로 가져온다** (아래 참조).

## autoNote 에서 가져올 것 / 버릴 것

### 가져올 것 (검증된 것)

| 가져올 것 | 왜 |
|---|---|
| **agy 워커 게이트웨이** | `--output-format json --json-schema` 로 출력을 스키마 강제. 실측으로 동작 확인됨 |
| **워커 로스터** (역할별 모델 배치) | 6개 모델 실측 비교 결과 보유. 문서화돼 있음 |
| **근거 검증** (숫자 대조) | AI 창작을 잡는 가장 값싼 수단. 토큰 0 |
| **배치 호출** | 호출당 고정 오버헤드 약 20.7k 토큰. 묶으면 47% 절감 실측 |
| **상태 체크포인트** | 실패 시 그 앞까지만 저장 → 다음 실행에서 자동 재시도 |
| **실패 알림 + 미실행 감시** | 두 가지 이상을 각각 다른 주체가 감지 |
| **잠금** | 문서 변경 작업 간 충돌 방지 |

### 버릴 것

| 버릴 것 | 대신 |
|---|---|
| Google Docs 를 저장소로 쓰기 | **SQLite 를 원천 저장소로**, 문서는 렌더링 결과물 |
| 줄 수 기반 필터 (`3줄 이하 제외`) | 워치리스트 사전 매칭 + AI 판별 |
| 평평한 모듈 구조 (`PYTHONPATH` 의존) | 처음부터 패키지 + editable 설치 |
| 문서 5곳 분산 | `docs/` 한 곳 |

## 성공 기준 (완료를 어떻게 판단하는가)

착수 전에 정해둔다. 나중에 "다 된 것 같은데?" 로 흐르지 않게.

| # | 기준 | 측정 방법 |
|---|---|---|
| 1 | N개 채널의 글이 **누락·중복 없이** 저장된다 | `SELECT COUNT(*), COUNT(DISTINCT ...)` 일치 |
| 2 | 워치리스트에 걸린 글을 **놓치지 않는다** | 표본 100건 수동 라벨링 대비 재현율 측정 |
| 3 | 관심 없는 글이 결과물에 **섞이지 않는다** | 같은 표본으로 정밀도 측정 |
| 4 | 하루 처리 **AI 비용이 예산 내** | 토큰 사용량 로그 집계 |
| 5 | AI가 **원문에 없는 내용을 만들지 않는다** | 근거 검증 위반 0건 |
| 6 | 실패하면 **내가 안다** | 알림 도달 확인 |
| 7 | 관심사가 바뀌면 **재처리로 대응된다** | 워치리스트 수정 → 재렌더 동작 |

> 2·3번(재현율·정밀도)은 **표본 라벨링이 선행되어야 측정 가능**하다. 착수 초기에 100건 정도 손으로 라벨링해두는 것을 권한다. 이게 없으면 "잘 되는 것 같다" 이상의 판단이 불가능하다.

## 단계 계획 (각 단계가 끝나면 쓸 수 있는 상태)

원칙: **한 단계가 끝나면 그 자체로 가치가 있어야 한다.** 전부 만든 뒤에 처음 돌려보는 방식을 피한다.

| 단계 | 만드는 것 | 끝나면 할 수 있는 것 |
|---|---|---|
| **P0** | 저장소 스키마 + 채널 1개 수집 | 원문이 DB 에 쌓인다. 조회 가능 |
| **P1** | 채널 N개 수집 + 중복 방지 | 여러 채널이 안정적으로 쌓인다 |
| **P2** | 워치리스트 사전 매칭 (AI 없음) | 관심 글을 규칙으로 걸러낸다. 비용 0 |
| **P3** | AI 관련성 판별 (배치) | 규칙이 놓친 것을 잡는다 |
| **P4** | AI 내용 추출 + 근거 검증 | 관심 글의 핵심이 정리된다 |
| **P5** | 렌더링 (다이제스트/문서) | 사람이 읽는 결과물이 나온다 |
| **P6** | 알림 + 감시 + 스케줄 | 자동으로 돌고, 실패하면 알려준다 |

**P2 까지만 해도 쓸 만하다.** AI 없이 규칙만으로 관심 글을 걸러내는 것이 이미 가치가 있고, 그 상태에서 AI 를 얹으면 개선 폭을 측정할 수 있다.
