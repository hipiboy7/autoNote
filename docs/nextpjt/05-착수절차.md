# 05. 착수 절차 — 첫 세션에서 무엇부터 할지

> **대상 독자:** 새 디렉토리에서 Claude Code 를 처음 켜는 나 자신
> **용도:** 순서대로 따라가면 P0(원문이 DB 에 쌓이는 상태)까지 도달한다
> **선행:** `00`~`04` 문서를 읽었다는 전제

---

## 0단계. 준비 (Claude Code 켜기 전)

- [ ] 새 디렉토리를 만든다 (예: `D:\rscope`)
- [ ] `docs/nextpjt/` 의 문서 5개를 새 프로젝트 `docs/` 로 복사한다
- [ ] `docs/00-신규프로젝트-설계교훈.md` 도 함께 복사한다 (**이게 제일 중요하다**)
- [ ] `04-AGENTS.md` 의 `---8<---` 사이 내용을 새 루트의 `AGENTS.md` 로 저장한다
- [ ] git 저장소를 초기화한다 (`git init`)

> **왜 문서를 먼저 옮기는가:** Claude Code 는 세션이 끊기면 맥락을 잃는다. 리포지토리 안의 문서는 남는다. autoNote 에서 세션이 여러 번 끊겼지만 `working_docs/` 덕분에 이어갈 수 있었다.

---

## 1단계. 요구사항 미결 항목 채우기 (Claude Code 없이 나 혼자)

`01-요구사항.md` 의 ❓ 항목을 채운다. **이걸 안 하고 코딩으로 넘어가지 않는다.**

가장 중요한 세 가지:

| 항목 | 왜 먼저 필요한가 |
|---|---|
| **대상 채널 목록** | 볼륨을 모르면 비용 설계가 불가능하다 |
| **초기 워치리스트** | 1단 필터의 정확도가 여기서 결정된다 |
| **결과물 형태** | 렌더링 설계가 달라진다 |

채널은 **3~5개로 시작**하는 것을 권한다. 처음부터 20개를 넣으면 볼륨·품질 편차 때문에 필터를 튜닝할 수 없다.

---

## 2단계. 첫 Claude Code 세션 — 이렇게 시작한다

아래를 그대로 붙여넣는다.

```
새 프로젝트를 시작한다. 다음 순서로 진행해줘.

1. docs/ 의 문서를 읽어라. 특히 00-신규프로젝트-설계교훈.md 의 8개 원칙과
   AGENTS.md 의 절대 규칙을 반드시 반영해라.

2. 03-디렉토리구조.md 대로 디렉토리와 pyproject.toml 을 만들어라.
   - 처음부터 패키지 구조 + editable 설치
   - .gitattributes 에 *.bat CRLF 고정 포함
   - .gitignore 에 자격증명·런타임 제외 포함

3. packages/core 부터 만들어라 (다른 것에 의존하지 않는 것부터).
   - db.py: SQLite 스키마 + 마이그레이션. 02-아키텍처.md 의 스키마 초안 사용
   - settings.py: 환경변수 → Settings 객체 (하드코딩 금지)
   - timebase.py: UTC 저장 / KST 표시 변환을 한 곳에서
   - 각각 테스트를 먼저 작성해라 (TDD)

4. editable 설치 후, 무관한 디렉토리에서 import 가 되는지 확인해라.
   그게 PYTHONPATH 의존이 없다는 증거다.

5. 여기까지 되면 멈추고 보고해라. 수집은 다음 단계다.

주의:
- 실패를 True 로 반환하는 함수를 만들지 마라
- 값·목록은 config/ 나 환경변수로 빼라
- 완료했다고 보고하기 전에 실제로 실행해서 확인해라
```

**이 프롬프트의 핵심은 "여기까지 되면 멈추라"** 다. 한 번에 전부 만들게 하면 검증 없이 쌓인다.

## 3단계. P0 완료 판정

아래가 되면 P0 완료다.

- [ ] `python -c "import rscope_core"` 가 무관한 디렉토리에서 성공
- [ ] `var/rscope.db` 가 생성되고 스키마가 들어가 있다
- [ ] 테스트가 통과한다
- [ ] 같은 메시지를 두 번 넣으면 두 번째가 무시된다 (UNIQUE 제약 동작 확인)
- [ ] UTC 로 저장된 시각이 KST 로 표시된다 (경계 케이스: UTC 23:xx → 다음날 KST)
- [ ] git 커밋이 되어 있다

**4번과 5번을 반드시 직접 확인할 것.** autoNote 에서 중복 방지와 시간대는 각각 298건·902건의 문제를 냈다. 이 두 가지가 처음부터 동작하는지가 이 프로젝트의 성패를 가른다.

---

## 4단계. 이후 단계 진행 방식

각 단계를 **별도 세션으로** 진행하고, 세션마다 이 패턴을 따른다.

```
1. docs/journal/ 최신 문서를 읽어 어디까지 됐는지 파악
2. 이번 단계 목표를 한 줄로 확인
3. 테스트 먼저 작성 → 구현 → 실제 실행 확인
4. 커밋
5. docs/journal/YYYY-MM-DD.md 에 기록
```

| 단계 | 목표 | 완료 판정 |
|---|---|---|
| P1 | 채널 N개 수집 | 3일 연속 돌려서 누락·중복 0 |
| P2 | 워치리스트 사전 매칭 | 표본 100건 대비 재현율·정밀도 측정치 확보 |
| P3 | AI 관련성 판별 | P2 대비 개선 폭이 수치로 보인다 |
| P4 | AI 추출 + 근거 검증 | 근거 검증 위반 0건 |
| P5 | 렌더링 | 결과물을 지우고 다시 만들 수 있다 |
| P6 | 알림 + 감시 + 스케줄 | 일부러 실패시켰을 때 알림이 온다 |

## 5단계. 표본 라벨링 (P2 전에 반드시)

**이게 없으면 필터가 잘 되는지 판단할 방법이 없다.**

방법:
1. 수집된 글에서 무작위 100건을 뽑는다
2. 각각에 대해 손으로 판정한다: 관련 있음 / 없음, 관련 있으면 어떤 대상인지
3. `var/labeled_sample.csv` 로 저장한다
4. 필터를 바꿀 때마다 이 표본으로 재현율·정밀도를 측정한다

100건이면 한 시간 정도 걸린다. **그 한 시간이 이후 모든 튜닝의 기준선이 된다.**

> **실무 비유:** 성능 개선을 할 때 개선 전 지표를 안 재두면 "빨라진 것 같다" 밖에 말할 수 없다. APM 없이 튜닝하는 것과 같다.

## 하지 말 것 (autoNote 에서 겪은 것)

| 하지 말 것 | 무슨 일이 있었나 |
|---|---|
| 전부 만든 뒤 처음 돌려보기 | 임시 구조가 그대로 운영에 들어갔다 |
| AI 키 없이 폴백으로 때우기 | 지어낸 내용 1,148건이 쌓였다 |
| 사람이 읽는 문서를 저장소로 쓰기 | 복구 작업 이틀, 일회성 스크립트 5개 |
| 런북에만 주의사항 적기 | 지켜지지 않았다. 코드로 막아야 한다 |
| AI 보고를 그대로 믿기 | "빌드 완료" 라던 기능이 없었다 |
| `PYTHONPATH` 로 경로 해결 | 12곳 복붙 → 장애 2회 |
| 테스트로 임시 동작 고정 | `assert apply_theme() is True` 가 no-op 을 명세로 굳혔다 |
