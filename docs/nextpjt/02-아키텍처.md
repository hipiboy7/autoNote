## 전체 그림

```
[텔레그램 N개 채널]
        │  수집 (프로그램, 토큰 0)
        ▼
┌─────────────────────────────────────────┐
│  원천 저장소 (SQLite)  ← 단일 진실       │
│  messages : append-only, UNIQUE 제약     │
└─────────────────────────────────────────┘
        │
        ├── 1단 필터 (프로그램, 토큰 0)
        │     워치리스트 사전 매칭
        │     ├─ 명백히 무관 → 제외 확정
        │     ├─ 명백히 관련 → 통과 확정
        │     └─ 애매 ─────────┐
        │                      ▼
        ├── 2단 필터 (AI 배치, 저렴)  관련성 판별
        │                      │
        ▼                      ▼
        └── 3단 추출 (AI 배치, 고품질)  내용 추출
                               │
                               │  근거 검증 (프로그램, 토큰 0)
                               │  통과 못하면 기록 안 함 → 재시도
                               ▼
┌─────────────────────────────────────────┐
│  파생 저장소 (같은 SQLite)               │
│  relevance / extractions : 재계산 가능   │
└─────────────────────────────────────────┘
        │  렌더링 (프로그램)
        ▼
[다이제스트 / 문서]  ← 지워도 다시 만들 수 있는 결과물
```

## 결정 1. 원천 저장소를 SQLite 로 둔다

### 근거
autoNote 는 Google Docs 가 유일한 저장소였고, 그 때문에 이런 일이 있었다.

| 문제 | 실측 | 저장소가 있었다면 |
|---|---|---|
| 중복 기록 | 298블록 | `UNIQUE` 제약으로 원천 차단 |
| 날짜 오기록 | 902건 | 렌더링 시점에 포맷 → 재렌더 |
| 창작 내용 기록 | 1,148건 | 추출 결과 재계산 |
| 중복을 눈으로 못 봄 | 몇 주간 미발견 | `GROUP BY ... HAVING COUNT(*)>1` |

### 왜 SQLite 인가

| 후보 | 판단 |
|---|---|
| **SQLite** | 파일 하나. 설치 불필요 → 폐쇄망 가능. 표준 SQL. 대학 때 배운 스키마·PK 개념 그대로 |
| PostgreSQL | 이 규모(하루 수천 건)에 과하다. 설치·운영 부담 |
| JSONL 파일 | 조회가 안 된다. 중복 검사를 코드로 해야 한다 |
| Google Docs | autoNote 에서 실패한 방식 |

> **실무 비유:** EAI 에서 원장(원천)과 전문(표현)을 구분하는 것과 같다. 전문을 원장으로 쓰면 재전송·포맷변경·조회가 모두 불가능해진다.

### 스키마 초안

```sql
-- 원천: append-only, 절대 수정하지 않는다
CREATE TABLE messages (
    channel_id   TEXT    NOT NULL,
    message_id   INTEGER NOT NULL,
    sent_at_utc  TEXT    NOT NULL,     -- ISO8601 UTC. 표시는 렌더링 때 KST 변환
    author       TEXT,
    text         TEXT    NOT NULL,
    collected_at TEXT    NOT NULL,
    PRIMARY KEY (channel_id, message_id)   -- ← 중복이 구조적으로 불가능
);

-- 채널별 진행 지점: 한 채널이 실패해도 나머지는 진행
CREATE TABLE channel_state (
    channel_id       TEXT PRIMARY KEY,
    last_message_id  INTEGER NOT NULL,
    last_run_utc     TEXT,
    last_result      TEXT,              -- ok | fail
    last_error       TEXT
);

-- 워치리스트: 설정 파일에서 동기화 (코드에 박지 않는다)
CREATE TABLE watchlist (
    key      TEXT PRIMARY KEY,          -- 'samsung_electronics'
    kind     TEXT NOT NULL,             -- company | industry | theme
    label    TEXT NOT NULL,             -- '삼성전자'
    aliases  TEXT NOT NULL,             -- JSON 배열: ["삼전","005930"]
    active   INTEGER NOT NULL DEFAULT 1
);

-- 파생: 관련성 판정 (재계산 가능)
CREATE TABLE relevance (
    channel_id  TEXT NOT NULL,
    message_id  INTEGER NOT NULL,
    stage       TEXT NOT NULL,          -- rule | ai
    relevant    INTEGER NOT NULL,
    matched     TEXT,                   -- JSON: 걸린 워치리스트 key 들
    reason      TEXT,
    decided_at  TEXT NOT NULL,
    PRIMARY KEY (channel_id, message_id),
    FOREIGN KEY (channel_id, message_id) REFERENCES messages(channel_id, message_id)
);

-- 파생: 내용 추출 (재계산 가능)
CREATE TABLE extractions (
    channel_id   TEXT NOT NULL,
    message_id   INTEGER NOT NULL,
    targets      TEXT NOT NULL,         -- JSON: 워치리스트 key 배열
    summary      TEXT NOT NULL,
    evidence     TEXT NOT NULL,         -- JSON 배열
    nature       TEXT NOT NULL,         -- fact | opinion | forecast
    model        TEXT,
    extracted_at TEXT NOT NULL,
    PRIMARY KEY (channel_id, message_id)
);

-- AI 호출 비용 추적
CREATE TABLE ai_usage (
    called_at    TEXT NOT NULL,
    worker       TEXT NOT NULL,
    model        TEXT NOT NULL,
    input_tokens INTEGER,
    output_tokens INTEGER,
    items        INTEGER,               -- 이 호출로 처리한 건수 (배치 효율 측정)
    duration_s   REAL
);
```

**검증 필요:** 스키마는 초안이다. 착수 시 실제 데이터로 조정한다.

## 결정 2. 3단 필터로 비용을 억제한다

### 근거 — 실측 수치

autoNote 실측: **AI 호출 1건당 input 약 20,700 토큰이 고정 오버헤드**다. 짧은 글 하나를 분석해도 22,000 토큰이 든다.

하루 1,000건을 전부 AI 에 보내면: `1,000 × 22,000 = 22,000,000 토큰`. 지속 불가능하다.

### 3단 구조

| 단계 | 처리량 (가정) | 방법 | 토큰 |
|---|---|---|---|
| 1단 | 1,000건 → 850건 제외 | 프로그램: 워치리스트 매칭 | **0** |
| 2단 | 150건 → 100건 제외 | AI 배치 (20건/호출) → 8회 | 약 200k |
| 3단 | 50건 추출 | AI 배치 (4건/호출) → 13회 | 약 400k |
| | | **합계** | **약 600k** |

건별 호출(22M) 대비 **약 36배 절감**. 위 수치는 가정이고, 실제 비율은 채널 성격에 따라 다르다 — **착수 후 실측해 이 표를 갱신할 것.**

### 1단 필터 설계 (가장 중요)

**여기서 걸러지는 비율이 전체 비용을 결정한다.**

```
제외 확정 (AI 안 보냄)
  - 본문 없음 (미디어 전용)
  - 링크만 (URL 제거 후 텍스트 없음)
  - 광고·공지·이벤트 키워드
  - 워치리스트 어느 항목도 언급 없음   ← 핵심

통과 확정 (2단 생략, 바로 3단)
  - 워치리스트 항목이 명확히 언급 + 충분한 길이

애매 (2단 AI 판별)
  - 워치리스트 항목 언급되나 단순 시세 나열
  - 별칭·간접 표현으로 걸린 경우
```

**주의:** autoNote 는 "URL 제거 후 3줄 이하 제외" 규칙을 썼고, 최근 200건 중 **118건(59%)** 이 탈락했다. 그중에 짧지만 핵심적인 판단 코멘트가 섞여 있었다. **줄 수는 가치의 지표가 아니다.** 이 프로젝트의 1단 필터는 "관심 대상 언급 여부"로 판단하고, 길이로 버리지 않는다.

## 결정 3. AI 계층은 추상화하고 스키마로 강제한다

### 인터페이스

```
WorkerRunner (추상)
  run(spec, prompt, schema) -> 검증된 객체
       │
       ├── AgyCliRunner       (agy CLI — autoNote 에서 검증됨)
       ├── OpenAIRunner       (필요 시)
       └── LocalModelRunner   (폐쇄망 대비)
```

**근거:** autoNote 는 OpenAI 전용으로 시작했다가 agy 로 갈아탈 때 게이트웨이를 새로 만들어야 했다. 추상화가 있었으면 값만 바꾸면 됐다.

### 워커 로스터 (역할별 모델)

autoNote 실측(2026-08-05, 동일 프롬프트/스키마) 기준. **이 프로젝트에서 다시 측정할 것.**

| 모델 | 시간 | total 토큰 | 판정 |
|---|---|---|---|
| gemini-3.1-pro-high | 22.7s | 23.3k | 정확·최소출력 → 추출용 |
| gemini-3.5-flash-medium | 22.7s | 22.2k | 대량 처리 → 판별용 |
| claude-opus-4-6-thinking | 55.4s | 27.9k | 논리 압축 최고 → 종합용 |
| gpt-oss-120b-medium | 82.0s | **331.2k** | **사용 금지** — 토큰 15배, 오분류, 도구로 파일 생성 시도 |

### 반드시 지킬 것

| 규칙 | 근거 |
|---|---|
| 출력을 **JSON 스키마로 강제** | 자유 텍스트는 파싱이 깨진다 |
| 분류 필드는 **enum** | autoNote 실측: 자유 문자열로 두니 존재하지 않는 테마 `"금지"`(금리의 오타)가 생성됨 |
| 실패 시 **중단, 창작 금지** | 1,148건 오염의 원인 |
| **배치로 묶기** | 고정 오버헤드 amortize |
| 프롬프트 길이 예산을 **프로그램이 관리** | Windows 명령행 길이 한계 등 |

## 결정 4. 근거 검증을 프로그램이 한다

### 방법
추출된 근거에 **원문에 없는 숫자가 있으면 실패**로 본다. AI 를 한 번 더 호출하지 않는다. 토큰 0.

```
근거: "블랙록 ETF에 11억 달러 유입 (비중 25%)"
원문: "블랙록 ETF에 저가 매수 자금이 집행되고 있음"
       → 11, 25 가 원문에 없다 → 창작. 기록하지 않는다
```

**실제로 이 검사로 잡은 사례다** (autoNote r404).

### 오탐 완화 (실측으로 조정된 규칙)

| 규칙 | 이유 |
|---|---|
| **한 자리 숫자는 검사하지 않는다** | `2분기`, `3일연속`, `2차` 같은 수량·서수 표현. 창작 수치는 거의 항상 두 자리 이상 |
| **연도 두 자리 표기 허용** | 원문 `2026년` ↔ 근거 `26년` 은 같은 값 |
| **원문 쪽은 관대하게** | 목록 번호가 뒤 숫자와 붙는 경우(`3.11월`) 대응 |
| **리스크·전망 항목은 검사 안 함** | 해석 영역이지 사실 주장이 아니다 |

> 이 완화 없이 돌렸을 때 오탐이 발생했다(5건 중 2건). **정상 글을 버리는 쪽을 더 경계**한다.

## 결정 5. 실패를 알 수 있게 만든다

감지해야 할 이상이 **두 가지이고 감지 주체가 다르다.**

| 유형 | 감지 주체 | 방법 |
|---|---|---|
| 돌았지만 실패 | 프로그램 자신 | 예외 포착 → 상태 기록 → 알림 → 종료코드 1 유지 |
| **아예 안 돎** | **별도 감시자** | 마지막 성공 시각이 임계치 초과 시 알림 |

**두 번째가 핵심이다.** 프로그램 안의 알림으로는 프로그램이 시작조차 못한 경우를 잡을 수 없다.

> **실무 비유:** APM 이 애플리케이션 안에서 돌면 애플리케이션이 죽을 때 알람도 같이 죽는다. 그래서 별도 감시 서버가 heartbeat 를 본다.

전달 경로는 **둘 이상 병행**하고, 알림 실패가 본 작업을 죽이지 않게 예외를 격리한다.

## 결정 6. 처음부터 설치 가능한 패키지로 만든다

### 근거
autoNote 는 `PYTHONPATH` 10개 경로 문자열이 12곳에 복붙돼 있었고, **실제로 두 번 장애를 냈다** (배치 파일에 경로 누락 → 배치 실패, 감시 스크립트 경로 부족 → import 오류).

### 방침
- 모듈을 평평하게 두지 않는다 (모듈명이 일반적이면 설치 시 다른 패키지와 충돌한다 — `watchdog` 은 실제 PyPI 패키지명이다)
- 처음부터 패키지 + `pip install -e` (또는 `uv`)
- 진입점은 `python -m <패키지>.<모듈>`

## 흐름 상세 (배치 1회)

```
1. 잠금 획득            ← 중복 실행·다른 작업과 충돌 방지
2. 채널별 수집
     for 채널 in 활성채널:
         마지막 지점 이후 조회 → messages 에 INSERT OR IGNORE
         채널별 진행 지점 갱신 (실패한 채널만 남기고 나머지 진행)
3. 1단 필터 (프로그램)   → relevance 에 rule 판정 기록
4. 2단 판별 (AI 배치)    → 애매한 것만 → relevance 에 ai 판정 기록
5. 3단 추출 (AI 배치)    → 관련 확정분 → 근거 검증 → extractions 기록
                            검증 실패분은 기록하지 않음 (다음 실행 재시도)
6. 렌더링                → 다이제스트/문서 생성
7. 상태 기록 + 실패 알림
```

**각 단계가 독립적으로 재실행 가능해야 한다.** 3단만 다시 돌리거나, 렌더링만 다시 하는 것이 되어야 한다.

## 열린 질문

- 워치리스트 매칭을 단순 문자열로 할지, 형태소 분석을 넣을지 (한국어 조사 처리)
- 같은 내용이 여러 채널에 퍼지는 경우(전달·인용) 중복 판정을 할지
- 관심사가 바뀔 때 과거 글을 재판정할지, 그때부터만 적용할지
- 추출 결과의 품질을 지속 측정할 방법 (표본 라벨링 갱신 주기)
