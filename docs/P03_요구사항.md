# 📋 Phase 3 요구사항 정의서: 구글 Docs 기록 및 생각노트 Pre-fill 개발

이 문서는 투자 리서치 수집 하이브리드 배치 프로그램의 세 번째 단계인 **구글 Docs 자동 기록 및 생각노트 Pre-fill 작성 모듈**에 대한 비즈니스 및 기능적 요구사항을 정의합니다.

---

## 1. 개요 및 비즈니스 목적
*   **목적:** 수집된 텔레그램 원문 및 AI 분석 결과를 지정된 구글 Docs에 서식에 맞게 기록하고, 사용자가 생각을 편하게 기록할 수 있도록 `99_생각노트` 문서에 입력 템플릿을 사전에 차려준다(Pre-fill).
*   **해결하려는 문제:** 구글 Docs API의 복잡한 요청(Request) 규격을 표준화하고, 가독성을 위한 세피아 크림 배경색 적용 및 사용자 입력을 유도하는 Pre-fill 작업을 자동화한다.

---

## 2. 기능적 요구사항 (Functional Requirements)

### 2.1 구글 Docs 기록 규칙 (기록 순서 및 서식)
*   **1단계: 원문 보관 (`00_원문보관 YYYY-MM`)**
    *   신규 수집된 **모든 메시지**를 날짜순으로 맨 아래에 추가(append)한다.
    *   형식:
        ```text
        ━━━━━━━━━━━━━━━━━━
        ■ YYYY-MM-DD | (핵심 한 줄 제목)
        ▶ 식별자: [r{message_id}]
        ▶ 출처: 피터케이 채널
        (원문 내용 그대로 기록)
        ```
*   **2단계: 테마/종목/프레임 노트 기록 (선별 대상만)**
    *   `is_research`가 참인 글은 분류된 테마(`10_테마 (테마명)`) 및 종목(`20_종목 (기업명)`) 문서의 맨 아래에 기록한다.
    *   형식 (테마/종목 공통):
        ```text
        ━━━━━━━━━━━━━━━━━━
        ■ YYYY-MM-DD | (핵심 한 줄 제목)
        ▶ 식별자: [t{message_id}] (또는 [s{message_id}])
        ▶ 출처: 피터케이 채널
        ▶ 핵심 주장: {LLM main_claim}
        ▶ 근거·데이터: {LLM evidence 목록}
        ▶ 판단 논리: {LLM logic}
        ▶ 리스크·반대 시나리오: {LLM risks 목록}
        ▶ 💭 내 생각: 미기록
        ▶ ❓ 생각해볼 질문: {LLM critical_question}
        ```
    *   식별자 접두사 매핑 규칙:
        *   원문보관: `[r{message_id}]`
        *   테마노트: `[t{message_id}]`
        *   종목노트: `[s{message_id}]`
        *   프레임노트: `[f{message_id}]`

### 2.2 가독성 향상 서식 (배경색 및 폰트)
*   리서치 Docs의 가독성을 높이기 위해, 문서 작성/업데이트 시 크림색 **세피아 테마 배경색(`#FDF6E3`, RGB: `0.992, 0.965, 0.890`)**을 일괄 적용한다.
*   구글 Docs의 `PageStyle` 또는 `DocumentStyle` API를 사용하여 문서 전체 배경색을 동적으로 보정한다.

### 2.3 생각노트 Pre-fill 자동 작성 (`99_생각노트`)
*   배치 작업 완료 시점에 `99_생각노트` 구글 문서 맨 아래에 그날 수집된 리서치 글의 생각 작성 창구를 자동으로 개설한다.
*   **생각노트 Pre-fill 서식:**
    ```text
    ━━━━━━━━━━━━━━━━━━
    ■ YYYY-MM-DD 생각노트 작성 창구
    - [t305] 삼성전자 반도체 공급망 분석 코멘트
      ▶ 💭 내 생각: 
    - [s305] 한화에어로스페이스 방산 전망 코멘트
      ▶ 💭 내 생각: 
    ```
*   사용자는 이 Pre-fill 항목의 `▶ 💭 내 생각: ` 뒤에 커서를 두고 자신의 생각을 직접 입력할 수 있다 (향후 Phase 4에서 자동 병합 대상이 됨).

## 3. 비기능적 요구사항 (Non-Functional Requirements)

### 3.1 Google Workspace API 의존성 격리
*   **DIP 원칙 준수:** 구글 Docs API 호출 코드를 직접 비즈니스 로직에 섞지 않고, 추상화 인터페이스 `DocsGateway`를 통해 캡슐화한다.
*   **API 쿼터 절약:** 여러 개의 쓰기 요청(InsertText, UpdateParagraphStyle 등)을 개별 API 호출 대신 `batchUpdate`를 사용하여 하나의 Request 청크로 묶어 처리한다.

### 3.2 테스트 가용성 (Testability)
*   Google API 자격 증명이나 네트워크 연결 없이 비즈니스 로직을 검증할 수 있도록 `MockDocsGateway`를 설계 및 활용한다.
*   배경색 변환, 식별자 생성, 문단 서식 변환, Pre-fill 템플릿 생성 로직의 코드 커버리지 95% 이상을 달성한다.
